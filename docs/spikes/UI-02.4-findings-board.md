# UI-02.4 — Findings triage board (Kanban)

Spike result for the Assurance add-in: the findings page of
`services/investigation-ui` is rebuilt as a findings **board**
(hash route `#/findings`, sidebar tab "Findings board") modelled on Craig's
Elera "Patient Flow" Kanban reference. No external runtime calls; everything
renders from the demo index plane, with the same textContent-only hostile-text
discipline (threat model T5) as the rest of the SPA.

## What shipped

- **Richer demo data** (`services/investigation-ui/demo_data/**`):
  - new `synthetic_audit_events.jsonl` — hand-built audit-plane INDEX rows
    (tool audits, custody events, identity chains, ingest coverage), every row
    explicitly `"synthetic": true` (honest markers; none of it touches the
    canonical `evidence_store.jsonl`), designed so **all eleven SEC rules fire
    somewhere** and `matched_degraded` + `trace_missing` correlation cases
    appear in the corpus;
  - `synthetic_receipt_index.jsonl` + `verification_index.jsonl` + `runs.json`
    extended with `run-sim-03` and its five traces: deny-correlated (SEC-004),
    bypass (SEC-001 + SEC-009), tool-call loop (SEC-005), hand-built
    `matched_degraded` (explicit `expected_correlation` override, notes carry
    the hand-built marker — the COR-01 engine has no fallback keys yet), and a
    trace-tagging defect case where a receipt row exists but its own trace id
    has no trace record (`trace_missing`), while the invocation itself is past
    grace = SEC-001;
  - `rules_fixture.json` documents demo suppressions for the new absence
    findings (GOV-01's report test requires the demo corpus to carry no active
    SEC-001; every absence in the demo corpus is now suppressed-with-reason).
- **Board view** in `static/index.html`:
  - KPI strip card: 4 groups split by 1px dividers, charcoal icon tiles,
    value + status pill (red "active findings", amber "unknown states" and
    "coverage findings", green "live"). KPI values are span-plane counts
    (`/api/findings/board` → `kpis`); the pills quote the findings-side
    counts (documented below — two lenses).
  - Filter row 1: scope pills (All / By rule / By run) + sort select
    (Most severe / Newest / Oldest) + find input.
  - Filter row 2: single-select counting chips — Needs investigation / Unproven /
    Coverage gaps / Resolved-closed / Suppressed ("(hidden by default)"), the
    active one in the dark charcoal token; right side shows
    "Showing X of Y findings" live.
  - 4 columns (lifecycle): New / Investigating / Suppressed / Resolved;
    header = name + count badge + right meta ("target: zero active" on
    Resolved); Resolved column is green-tinted and always carries the
    **summary card** (aggregate rows + progress bar).
  - Finding card: charcoal number tile + rule name + reason line (finding
    explanation); token row = severity pill (red/amber/green tint), relative
    time pill with clock icon (red stale > 24h, amber > 1h), run chip, state
    chip. Clicking a card elevates it (bigger shadow) and reveals the inline
    **amber finding note**: the four-part guidance copy condensed to the
    finding sentence + first suggested action + evidence ref, plus
    'Open full guidance in the drilldown' (run-linked) or an inline
    full-guidance expander for corpus-level findings.
  - Context action per card derived from the rule (SEC-004 → "Compare
    tool-side event", SEC-001 → "Corroborate coverage", …). The one real
    endpoint the add-in serves (offline receipt verify, SEC-002) is wired to a
    receipt-backed action; everything else shows the honest
    `action stub: alpha` toast — no fake results.
  - All-clear: when no open findings exist a green banner renders; the
    Resolved column keeps the summary card.
- **Demo state model (alpha)**: cards move New → Investigating → Resolved via
  the per-card state button (cycles; a suppressed card shows the dark
  "Restore" and moves back to New). Persistence is a UI-sidecar index —
  `POST /api/findings/{id}/triage` writes `demo_data/triage_state.json`
  (default state derives from the finding: fixture-suppressed → Suppressed
  column, everything else → New). The canonical evidence store is never
  written (invariant 1).

## Reconcilability (chip counts = member counts)

Each row-2 chip's count is literally the number of its member cards:

| chip        | member predicate                                        |
|-------------|---------------------------------------------------------|
| Needs investigation | open (state new/investigating) ∧ lens = needs   |
| Unproven            | open ∧ lens = unproven                          |
| Coverage gaps       | open ∧ lens = gaps                              |
| Resolved/closed     | state = resolved                                |
| Suppressed          | state = suppressed (hidden unless selected)     |

The lens is a rule-level risk classification (`LENS_BY_RULE` in
`app.py`): needs = SEC-004/008/009/010 (discrepancy needing an
investigator decision), unproven = SEC-002/003/005/006/011 (evidence exists,
less than full proof), gaps = SEC-001/007 (absence rules). KPI-strip values
come from a different lens (span-plane verification/correlation states) —
the KPI pills state the findings-side member counts so the two lenses are
visible next to each other. Covered by reconciliation tests in
`tests/test_findings_board.py`.

## Known alpha limits

- No drag-and-drop and no '+ Add' — state moves are the per-card button.
- `matched_degraded` is a hand-built override of the COR-01 engine output
  (engine emits no fallback-pairing state yet); the record notes keep the
  hand-built marker.
- Relative-time pills use the wall clock at render time over fixed fixture
  instants; ages drift (the >24h stale demo rows go redder over days).
- Board triage state is additive demo-sidecar state; production would write
  through a findings/ticket backend instead.
## UI-05 coherence pass: column/chip/KPI mapping

Single taxonomy, one source: every count on the board now derives from
`counting.count_evidence` served on `GET /api/counts` (see
`docs/spikes/coherence-pass.md`).

- Columns = lifecycle states (4): **Needs investigation** (state `new`),
  **Investigating**, **Suppressed**, **Closed** (green-tinted; the earlier
  'Resolved' label and internal key are replaced by `closed`).
- Counting chips = risk lens over OPEN findings: **Needs investigation**
  (`needs`) / **Unproven** (`unproven`) / **Coverage gaps** (`gaps`), plus
  the terminal **Closed** and **Suppressed** chips. The three lens chips
  partition the open findings exactly; Closed/Suppressed pick out exactly
  their column members.
- Coverage gaps is deliberately NOT a column: it is a chip + KPI metric
  (the spec's QA decision). A coverage-gap finding still occupies its
  lifecycle column; the chip filters/tag it.
- KPI strip numbers == chip counts == member counts of the same buckets:
  needs 4 · unproven 5 · coverage gaps 1 · evidence verified 8
  (index-plane metric with a real count, labelled 'index-plane').
- Board outcome card: Closed + Suppressed + Open = total, computed over
  the shown set (so it stays coherent under search/chip filters), and
  'Open' equals the items visible across the open columns.
